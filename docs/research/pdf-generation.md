# PDF Generation for HOA Dues Bills — Research

**Scope:** Laravel 13 / PHP 8.5 app. Need to print ~150–300 single-page dues bills once a month (letterhead, property identifier, billing period, a handful of fee line items, amount due) on A4 or Letter paper, for households not on the platform.

**Method:** Primary sources only — package `composer.json` files pinned to tagged GitHub releases, Packagist package-version JSON, packages' own docs/READMEs/wikis, packages' own GitHub Actions CI workflow files (to check what PHP versions are _actually run in the packages' own test suites_, not just permitted by a composer constraint), and Laravel's own release notes. Secondary write-ups were not used as sources of truth. Research date: 2026-09-06. All version/date figures below were current as of that date and can drift — re-check Packagist before acting on this.

---

## 1. Summary

For a simple, static, letterhead-style single-page bill printed in batches of 150–300 once a month, a pure-PHP HTML/CSS-to-PDF renderer is the better architectural fit: it needs no headless-browser runtime, has a much lower per-document cost, and this bill's layout (a letterhead, a few text blocks, a small line-item table, a total) does not need flexbox or CSS grid. Both **dompdf** (directly, or via **barryvdh/laravel-dompdf**) and **mpdf** satisfy this. On PHP 8.5 specifically, the picture is more nuanced than "compatible" vs "not": **mpdf/mpdf** is the only candidate whose published `composer.json` explicitly lists `~8.5.0` in its PHP constraint _and_ whose own GitHub Actions CI matrix actually runs its test suite against PHP 8.5 — this is the strongest evidence of any candidate here. **spatie/laravel-pdf**, **barryvdh/laravel-dompdf**, and **spatie/browsershot** all have open-ended PHP constraints (no stated upper bound) but their own CI workflows _do_ include a `php: 8.5` entry in the test matrix, meaning the wrapper code itself is exercised on PHP 8.5 in CI even though the package's `composer.json` doesn't say so explicitly. The one gap worth flagging plainly: **dompdf/dompdf itself — the actual rendering engine underneath `barryvdh/laravel-dompdf` and spatie/laravel-pdf's DOMPDF driver — has not yet added PHP 8.5 to its own CI matrix** (it tops out at 8.4 as of this research date), even though its composer constraint (`^7.1 || ^8.0`) permits installing on 8.5. **spatie/laravel-pdf** is also the most flexible option (it now wraps six different rendering backends behind one API, including dompdf itself and Browsershot/headless Chrome) and is worth considering as the app's PDF _facade_ even if the DOMPDF driver is what actually runs in production, because it gives a documented, CI-tested escape hatch to a Chromium-based renderer later if bill layouts grow more complex. This is engineering input for a human to weigh, not a final decision — see [Recommendation](#4-recommendation).

## 3. Per-candidate sections

### 3.1 spatie/laravel-pdf

**Laravel 13 / PHP 8.5 compatibility.** Latest Packagist release at research time: **2.13.1**, published **2026-09-01** — [Packagist](https://packagist.org/packages/spatie/laravel-pdf). Its tagged `composer.json` states, verbatim:

```
"require": {
    "php": "^8.2",
    "illuminate/contracts": "^11.0|^12.0|^13.0",
    "spatie/laravel-package-tools": "^1.16.1",
    "spatie/temporary-directory": "^2.2.1"
}
```

— [composer.json@2.13.1](https://github.com/spatie/laravel-pdf/blob/2.13.1/composer.json)

This explicitly allows Laravel 13 (`illuminate/contracts ^13.0`). PHP support is stated as `^8.2` with **no upper bound** in `composer.json` — on the constraint text alone this is case **(b)** from the task brief. However, the package's own CI workflow (`.github/workflows/run-tests.yml`) runs a matrix that explicitly includes `php: 8.5` together with `laravel: 13.*` (`stability: prefer-lowest`) — [run-tests.yml](https://github.com/spatie/laravel-pdf/blob/main/.github/workflows/run-tests.yml). So while the shipped `composer.json` doesn't pin an upper PHP bound, the maintainers' own test suite _is_ actually being run against PHP 8.5 + Laravel 13 as of this research date — stronger evidence than the bare constraint suggests, even if it stops short of a formal "supported PHP versions" statement in the docs. Note also that this is a major architectural change from the 1.x line: as of 2.x, `spatie/browsershot` is no longer a hard `require` — it moved to `suggest` alongside `dompdf/dompdf`, `chrome-php/chrome`, and `tecnickcom/tc-lib-pdf-encrypt`, because the package became a multi-driver facade (see below). The 1.x line (`illuminate/contracts ^10.0|^11.0|^12.0`, last release 1.9.0, 2026-01-31) hard-required Browsershot and did not support Laravel 13's `^13.0` illuminate constraint.

**Runtime requirements.** The package's own README states: "This package provides a simple way to create PDFs in Laravel apps. It supports multiple drivers: Browsershot (Chromium), Gotenberg (Docker-based), Cloudflare Browser Run, WeasyPrint (Python-based), DOMPDF (pure PHP), and chrome-php/chrome (Chromium)." — [README@2.13.1](https://github.com/spatie/laravel-pdf/blob/2.13.1/README.md). Per the package's own drivers documentation:

- **Browsershot (default)**: "Requires Node.js and a Chrome/Chromium binary."
- **Chrome PHP**: requires a "Chrome/Chromium 65+ executable."
- **Gotenberg**: requires Docker.
- **WeasyPrint**: requires the WeasyPrint binary (Python-based).
- **Cloudflare**: "No Node.js or Chrome binary needed" — calls Cloudflare's hosted Browser Rendering API over HTTP.
- **DOMPDF**: "No external binaries, no Node.js, no Docker — works everywhere PHP runs."

— [drivers docs](https://spatie.be/docs/laravel-pdf/v2/drivers/using-a-driver)

The default driver is Browsershot unless changed. Config: `'driver' => env('LARAVEL_PDF_DRIVER', 'browsershot')`, with documented supported values `browsershot`, `chrome`, `cloudflare`, `dompdf`, `gotenberg`, `weasyprint` — [drivers configuration docs](https://spatie.be/docs/laravel-pdf/v2/drivers/configuration). Driver can also be overridden per call: `Pdf::view(...)->driver('dompdf')->save(...)`.

**Blade rendering and CSS support.** `Pdf::view('pdfs.invoice', ['invoice' => $invoice])->format('a4')->save('invoice.pdf')` renders a Blade view directly — no manual `->render()` step needed — [README@2.13.1](https://github.com/spatie/laravel-pdf/blob/2.13.1/README.md). CSS capability is inherited entirely from the active driver: the four Chromium/Docker/cloud-Chromium drivers (Browsershot, Chrome PHP, Gotenberg, Cloudflare) "support modern CSS features like grid and flexbox, or even a framework like Tailwind"; WeasyPrint is called out for "excellent CSS Paged Media support," useful for repeating headers/footers and page counters; DOMPDF "supports CSS 2.1 and some CSS 3 properties, making it ideal for simpler PDFs" — [drivers docs](https://spatie.be/docs/laravel-pdf/v2/drivers/using-a-driver). Reading the package's own `DomPdfDriver.php` source confirms the DOMPDF driver is a thin wrapper: it builds a `Dompdf\Dompdf` instance, injects header/footer HTML and a `@page { margin: ... }` block, then calls `$dompdf->setPaper($format, $orientation)` — so DOMPDF-driver CSS support is byte-for-byte dompdf's own CSS support (see §3.3) — [DomPdfDriver.php@2.13.1](https://github.com/spatie/laravel-pdf/blob/2.13.1/src/Drivers/DomPdfDriver.php).

**Batch generation of 150–300/run.** No package-published numbers on throughput or memory for batch runs were found in the README, docs site, or composer metadata. Qualitatively: on the DOMPDF or Cloudflare drivers there is no local browser-process overhead per document, so 150–300 sequential PDFs is architecturally identical to running dompdf directly (§3.3). On the Browsershot or Chrome-PHP drivers, each `->save()` call is, per Browsershot's own README, done "behind the scenes by Puppeteer which runs a headless version of Google Chrome" — [Browsershot README](https://github.com/spatie/browsershot/blob/5.4.0/README.md) — i.e., process/browser-launch overhead is architecturally inherent per document unless the calling code explicitly reuses a browser instance (not the package's documented default usage pattern). No published benchmark quantifies this overhead in seconds or MB. (`spatie/browsershot` itself: latest Packagist release **5.4.0**, published 2026-05-26, `php ^8.2` in composer.json with no stated upper bound, but its own CI matrix — like laravel-pdf's — explicitly runs `php: 8.5` — [run-tests.yml](https://github.com/spatie/browsershot/blob/main/.github/workflows/run-tests.yml).)

**Paper size handling.** `->format(Format::A4)` / `->format(Format::Letter)` (or the raw strings `'a4'`, `'letter'`) — the package ships a PHP enum with the values `Letter, Legal, Tabloid, Ledger, A0..A6` — [Format.php@2.13.1](https://github.com/spatie/laravel-pdf/blob/2.13.1/src/Enums/Format.php). Orientation is a separate `->landscape()` / `->portrait()` / `->orientation(...)` call — [PdfBuilder.php@2.13.1](https://github.com/spatie/laravel-pdf/blob/2.13.1/src/PdfBuilder.php). These are passed through to whichever driver is active (e.g. the DOMPDF driver translates them into a `Dompdf::setPaper($format, $orientation)` call).

**Laravel's own official guidance mentioning this package.** Laravel Cloud's own knowledge-base explicitly recommends spatie/laravel-pdf, configured with its Cloudflare driver, for PDF generation on Laravel Cloud specifically, and notes: "Cashier's default invoice PDF renderer uses Dompdf, which does not work in Laravel Cloud." — [Laravel Cloud: Generating PDFs](https://laravel.com/cloud/docs/knowledge-base/generating-pdfs). This caveat is scoped to Laravel Cloud's serverless/ephemeral-filesystem hosting model — it is not a general statement that dompdf doesn't work on ordinary servers, and this app is not stated to run on Laravel Cloud, but it does show Laravel's own docs treating spatie/laravel-pdf as the "officially blessed" community PDF package.

### 3.2 barryvdh/laravel-dompdf

**Laravel 13 / PHP 8.5 compatibility.** Latest Packagist release: **v3.1.2**, published **2026-02-21** — [Packagist](https://packagist.org/packages/barryvdh/laravel-dompdf). Tagged `composer.json`, verbatim:

```
"require": {
    "php": "^8.1",
    "dompdf/dompdf": "^3.0",
    "illuminate/support": "^9|^10|^11|^12|^13.0"
}
```

— [composer.json@v3.1.2](https://github.com/barryvdh/laravel-dompdf/blob/v3.1.2/composer.json)

`illuminate/support ^13.0` explicitly allows Laravel 13. PHP support is `^8.1`, open-ended with no upper bound in `composer.json` — the constraint alone is case **(b)**. But this package's own CI workflow matrix explicitly includes `php: 8.5` combined with `laravel: 13.*` — [run-tests.yml](https://github.com/barryvdh/laravel-dompdf/blob/master/.github/workflows/run-tests.yml) — so the Laravel-integration layer (facade, service provider, config) is actually exercised against PHP 8.5 + Laravel 13 in CI. That said, this package is a thin wrapper: the actual HTML/CSS rendering happens inside `dompdf/dompdf`, and — as detailed in §3.3 — dompdf's own CI matrix does not yet include PHP 8.5 at all. So "the Laravel glue is CI-tested on 8.5" and "the rendering engine is CI-tested on 8.5" are two different, and currently different-valued, claims.

**Runtime requirements.** Pure PHP — this package is a thin Laravel service-provider/facade wrapper around `dompdf/dompdf` (`^3.0`, satisfied by dompdf's latest 3.1.6); it inherits dompdf's own extension requirements (`ext-dom`, `ext-mbstring`; `ext-gd`/`ext-imagick` suggested for images — see §3.3). Its own readme describes installation as simply `composer require barryvdh/laravel-dompdf`, "This will download the package and the dompdf + fontlib libraries also." — [readme.md@v3.1.2](https://github.com/barryvdh/laravel-dompdf/blob/v3.1.2/readme.md).

**Blade rendering and CSS support.** Direct Blade rendering via the facade: `Pdf::loadView('pdf.invoice', $data); return $pdf->download('invoice.pdf');` — quoted verbatim from its own readme — [readme.md@v3.1.2](https://github.com/barryvdh/laravel-dompdf/blob/v3.1.2/readme.md). You can also load a raw HTML string (`Pdf::loadHTML('<h1>Test</h1>')`) or a file (`Pdf::loadFile(...)`). CSS support is exactly dompdf's own (see §3.3), since this package does not modify dompdf's rendering — it only wires dompdf into Laravel's config/facade system and exposes a `config/dompdf.php` file (`defaultPaperSize`, `defaultFont`, `chroot`, `tempDir`, `fontDir`, etc.) — [readme.md@v3.1.2](https://github.com/barryvdh/laravel-dompdf/blob/v3.1.2/readme.md).

**Batch generation of 150–300/run.** No batch-specific guidance in this wrapper's own docs. Because it does not spawn any external process, generating 150–300 documents in one PHP run/queue job is architecturally the same cost as calling dompdf directly 150–300 times (see §3.3) plus negligible facade overhead.

**Paper size handling.** `Pdf::loadHTML($html)->setPaper('a4', 'landscape')->save('myfile.pdf')` — quoted verbatim — or set the `defaultPaperSize` key ("a4" by default) in `config/dompdf.php` after `php artisan vendor:publish` — [readme.md@v3.1.2](https://github.com/barryvdh/laravel-dompdf/blob/v3.1.2/readme.md).

### 3.3 dompdf/dompdf (the underlying engine)

**Laravel 13 / PHP 8.5 compatibility.** dompdf/dompdf is not Laravel-aware (no `illuminate/*` constraint at all) — Laravel compatibility is entirely a function of the wrapper (barryvdh/laravel-dompdf, or spatie/laravel-pdf's DOMPDF driver). Latest Packagist release: **v3.1.6**, published **2026-07-20** — [Packagist](https://packagist.org/packages/dompdf/dompdf). Tagged `composer.json`, verbatim:

```
"require": {
    "php": "^7.1 || ^8.0",
    "ext-dom": "*",
    "ext-mbstring": "*",
    "masterminds/html5": "^2.0",
    "dompdf/php-font-lib": "^1.0.0",
    "dompdf/php-svg-lib": "^1.0.0"
}
```

— [composer.json@v3.1.6](https://github.com/dompdf/dompdf/blob/v3.1.6/composer.json)

This is a very broad, open-ended PHP constraint (`^7.1 || ^8.0` covers everything from PHP 7.1 through any future 8.x, including 8.5) with no explicit mention of PHP 8.5 anywhere in the file or in the CHANGELOG for this tag. Checking dompdf's own CI workflow confirms this is not just an artifact of a loose constraint string but reflects the actual state of testing: the `matrix.php` list in `.github/workflows/test.yml` (checked against the `master` branch, 2026-09-06) is `['7.1', '7.2', '7.3', '7.4', '8.0', '8.1', '8.2', '8.3', '8.4']` — **PHP 8.5 is absent from dompdf's own test matrix** — [test.yml](https://github.com/dompdf/dompdf/blob/master/.github/workflows/test.yml). This is squarely case **(c)** from the task brief for the _rendering engine specifically_: genuinely unclear/untested, not merely "implied." Since this app's PHP 8.5 support ultimately rests on dompdf's actual parsing/layout code (not just the wrapper), this is the most concrete gap found in this research.

**Runtime requirements.** Pure PHP, "works everywhere PHP runs" (per spatie/laravel-pdf's own characterization of the DOMPDF driver, corroborated by dompdf's `composer.json` requiring only PHP + two core extensions). Required: `ext-dom`, `ext-mbstring`. Suggested (not required): `ext-gd` ("Needed to process images"), `ext-imagick`/`ext-gmagick` ("Improves image processing performance"), `ext-zlib` ("Needed for pdf stream compression") — [composer.json@v3.1.6](https://github.com/dompdf/dompdf/blob/v3.1.6/composer.json).

**Blade rendering and CSS support.** dompdf has no Blade awareness at all (it's not a Laravel package) — the calling app must render the view to an HTML string itself (`$html = view('pdfs.invoice', $data)->render();`) and pass that string to `$dompdf->loadHtml($html)`. CSS support is documented in dompdf's own GitHub wiki, in an explicit per-property support table. Quoting verbatim from that table (`dompdf/dompdf` wiki, page `CSSCompatibility`):

- `@page` — `yes`; `@page :left`/`:right`/`:odd`/`:even`/`:first` — `yes`, but "only margins are applied"
- `display` — `partial` — "Display type `run-in` is not supported" (there is no `flex` or `grid` value listed anywhere in the supported `display` values or elsewhere in the document — flexbox/grid layout is simply absent from the table)
- `page-break-after` / `page-break-before` — `yes` — "Supported on table rows since 1.1.0. Not supported on table row groups"
- `page-break-inside` — `yes` — "Not supported on table row groups"
- `float` / `clear` — `partial`
- `max-height` / `min-height` — `partial`
- `box-shadow`, `box-sizing`, `text-shadow`, `direction`, `font-stretch`, `font-variant` — `no`
- `size` — `yes` — "for @page"

— [dompdf CSSCompatibility wiki](https://github.com/dompdf/dompdf/wiki/CSSCompatibility)

dompdf's own README describes the library as "a CSS 2.1 compliant HTML to PDF converter" — [composer.json@v3.1.6 description field](https://github.com/dompdf/dompdf/blob/v3.1.6/composer.json). For this app's specific bill layout (letterhead block, a few text lines, a fee table, a total) none of the unsupported/partial items above (flexbox, grid, box-shadow, `run-in` display, table-row-group page breaks) look load-bearing — a table-based or block/inline layout with `@page` margins and `page-break-inside: avoid` on individual rows is squarely in dompdf's supported set.

**Batch generation of 150–300/run.** dompdf's own wiki has a dedicated `Performance` page. Quoting it in full (it is short):

> "## Layout
>
> - Minimize use of tables
> - Keep your document as small as possible
>   -- use fewer tags
>   -- break very large documents into separate renders
> - Disable the HTML5 parser if the HTML document is validly structured
>
> ## Styling
>
> - Exclude unused styles
>
> ## Images
>
> - Use JPEG images to avoid extra parsing required for transparency and or conversion
>   -- Except for background images, which always go through extra processing
> - Use the IMagick/GMagick extensions
>
> ## Metrics
>
> _todo_"

— [dompdf Performance wiki](https://github.com/dompdf/dompdf/wiki/Performance)

Note the "Metrics" section is explicitly marked `*todo*` in dompdf's own docs — **there is no published number for memory ceiling, per-document render time, or a maximum batch size**. This guidance is about keeping any _single_ document small/simple, not about running many documents in one PHP process; nothing in the docs discourages calling dompdf 150–300 times in a loop or a queued job. A handful of GitHub issues (anecdotal, not authoritative — flagged as such per the task brief) report out-of-memory conditions on dompdf, e.g. [#1956](https://github.com/dompdf/dompdf/issues/1956) ("image causing out of memory"), [#528](https://github.com/dompdf/dompdf/issues/528) ("Long table causing memory/timeout errors"), [#408](https://github.com/dompdf/dompdf/issues/408) ("memory limit exhausted") — these are all about a single large/complex document, not a documented batch-count ceiling, and a one-page letterhead bill is far smaller than the documents in those reports.

**Batch generation, quantified vs. headless Chrome.** Neither dompdf's nor Browsershot's own docs give a concrete number (ms/doc, MB/doc) for either approach, so this cannot be quantified from primary sources. Qualitatively: dompdf runs entirely in-process (no subprocess, no IPC), so its per-document cost is essentially "however long PHP takes to lay out and rasterize this one document," repeatable in a tight loop with no fixed floor cost. Browsershot, by its own README, does its work "behind the scenes by Puppeteer which runs a headless version of Google Chrome" — [Browsershot README](https://github.com/spatie/browsershot/blob/5.4.0/README.md) — meaning every call incurs a Chromium process launch/render/teardown cycle unless the calling code is written to keep one browser instance open across many calls (not how Browsershot's own quick-start examples call it). A Chrome process launch is inherently much heavier than an in-process PHP function call — this is an architectural inference from how Browsershot is documented to work, not a benchmarked number from either project's own docs.

**Paper size handling.** `$dompdf->setPaper('letter', 'portrait')` or `'a4'` (dompdf's own `setPaper()` method, accepting named paper sizes or a custom `[x1,y1,x2,y2]` box), or a CSS `@page { size: A4; }` rule — dompdf's own compatibility table lists `size` as `yes ... for @page` — [dompdf CSSCompatibility wiki](https://github.com/dompdf/dompdf/wiki/CSSCompatibility).

### 3.4 mpdf/mpdf

**Laravel 13 / PHP 8.5 compatibility.** Latest Packagist release: **v8.3.1**, published **2026-03-11** — [Packagist](https://packagist.org/packages/mpdf/mpdf). Tagged `composer.json`, verbatim `require.php` entry:

```
"php": "^5.6 || ^7.0 || ~8.0.0 || ~8.1.0 || ~8.2.0 || ~8.3.0 || ~8.4.0 || ~8.5.0",
```

— [composer.json@v8.3.1](https://github.com/mpdf/mpdf/blob/v8.3.1/composer.json)

This is case **(a)** — **explicitly declared**. mpdf's own `composer.json` literally lists `~8.5.0` as an allowed constraint, which is a stronger, more concrete statement than any other candidate researched here made about PHP 8.5. Checking the Packagist version history shows this constraint (with `~8.5.0` present) was already published in **v8.2.6 (2025-08-18)** — i.e. before PHP 8.5.0's official GA release on **2025-11-20** ([php.net PHP 8.5 release announcement](https://www.php.net/releases/8.5/en.php)) — meaning mpdf's maintainers added the constraint during PHP 8.5's beta/RC cycle. This is corroborated by mpdf's own CI: its `.github/workflows/tests.yml` `matrix.php-version` list (checked against the `development` branch, which is the repo's default branch, 2026-09-06) explicitly includes `"8.5"` alongside `"8.4"`, `"8.3"`, etc., run on both `ubuntu-latest` and `windows-latest` — [tests.yml](https://github.com/mpdf/mpdf/blob/development/.github/workflows/tests.yml). Of every candidate in this research, mpdf is the only one where PHP 8.5 support is both **stated in the composer constraint** and **actively exercised in the project's own CI** — the two other packages with promising CI evidence (spatie/laravel-pdf, barryvdh/laravel-dompdf) test PHP 8.5 in CI without yet reflecting it in their composer constraint text. No `illuminate/*` dependency exists — mpdf is not a Laravel package, so Laravel-version compatibility is not something its own files speak to; it works in any PHP context including Laravel controllers/jobs.

**Runtime requirements.** Pure PHP. `composer.json` requires `ext-gd`, `ext-mbstring`, plus a handful of small pure-PHP composer dependencies (`mpdf/psr-log-aware-trait`, `myclabs/deep-copy`, `setasign/fpdi`, etc.) — [composer.json@v8.3.1](https://github.com/mpdf/mpdf/blob/v8.3.1/composer.json).

**Blade rendering and CSS support.** No Blade integration ships with the package (mpdf is framework-agnostic) — the calling code must render the Blade view to a string and call `$mpdf->WriteHTML($html)`. Paper/format config is set through the constructor's config array. Per mpdf's own docs page on the constructor: the `format` key "Can be specified either as a pre-defined page size, or as an array of width and height in millimetres," default `'A4'`; predefined values include `'A0'`–`'A10'`, `'Letter'`, `'Legal'`, and any of these suffixed `-L` to force landscape (e.g. `'A4-L'`) — [mpdf construct reference](https://mpdf.github.io/reference/mpdf-functions/construct.html). Per mpdf's own supported-CSS docs, it implements "CSS2.1 with CSS3 extensions," documents support for `page-break-before`/`page-break-after`/`page-break-inside`, and a `@page` at-rule supporting "size, sheet-size, margin properties, marks, header, footer, and background properties" (with the caveat that "left and right margins cannot be changed when using a page selector"). It documents multiple explicit mechanisms for repeated headers/footers ("runtime non-HTML," "runtime HTML," "named non-HTML," "named HTML," selected via `odd-header-name`/`even-header-name`/`odd-footer-name`/`even-footer-name` in `@page` rules). Flexbox and CSS grid are not mentioned anywhere in mpdf's own supported-CSS documentation — [mpdf supported-css docs](https://mpdf.github.io/css-stylesheets/supported-css.html).

**Batch generation of 150–300/run.** No process spawn per document (pure PHP, same profile as dompdf). No published batch/throughput numbers were found in mpdf's own docs site.

**Paper size handling.** Constructor config key `format`, e.g. `new \Mpdf\Mpdf(['format' => 'A4'])`, `new \Mpdf\Mpdf(['format' => 'Letter'])`, or `new \Mpdf\Mpdf(['format' => 'A4-L'])` for landscape; a custom `[width_mm, height_mm]` array plus `'orientation' => 'P'|'L'` is also supported — quoted from mpdf's own constructor reference docs — [mpdf construct reference](https://mpdf.github.io/reference/mpdf-functions/construct.html).

### 3.5 TCPDF / tecnickcom/tc-lib-pdf (checked for completeness)

Included per the task brief's instruction to check other actively-maintained options. Finding: TCPDF, as a project, explicitly declares itself **deprecated by its own maintainers**. Quoting its README verbatim, top of file:

> "# TCPDF (DEPRECATED → use tc-lib-pdf)
>
> **TCPDF is in maintenance-only mode.** Active development has moved to **tc-lib-pdf**, its modern, modular successor — new projects should start there."

— [README@7.0.8](https://github.com/tecnickcom/TCPDF/blob/7.0.8/README.md)

The GitHub repository's own description field states the same thing even more tersely: "Deprecated: PHP PDF library, superseded by tc-lib-pdf" (confirmed via the GitHub API repository metadata for `tecnickcom/TCPDF`, checked 2026-09-06; the repo is not archived and did receive a push as recently as 2026-09-05, i.e. it is in active maintenance-only mode, not abandoned, but new feature work is explicitly directed elsewhere). Since version 7, the `tecnickcom/tcpdf` package (composer.json: `"php": ">=8.2"`, requiring `tecnickcom/tc-lib-pdf ^8.73.5` — [composer.json@7.0.8](https://github.com/tecnickcom/TCPDF/blob/7.0.8/composer.json)) is itself only a backward-compatibility facade over the new `tecnickcom/tc-lib-pdf` engine, per its own README: "Starting with version 7, the `TCPDF` class no longer contains its own PDF engine. It is a **compatibility facade**... Output is structurally equivalent, not byte-identical."

Neither the legacy `TCPDF` class nor `tc-lib-pdf` renders a Blade view or arbitrary CSS-styled HTML directly — both are imperative, method-call-driven PDF composition APIs (`AddPage()`, `SetFont()`, `Cell()`, `Write()`), with an optional `writeHTML()` method for inserting HTML fragments, not a CSS-cascade-driven full-page layout engine. This makes it a poor fit for "design the bill as a Blade view with CSS" — the workflow this task is optimizing for — compared to dompdf/mpdf/laravel-pdf, all of which take a full HTML+CSS document as input. Given both the maintainers' own deprecation notice and the mismatch with a Blade/CSS-driven authoring workflow, TCPDF is not recommended for this project even though it remains installable and technically functional.

## 4. Recommendation

**This section is input for a human to weigh — not a decision.** Whoever picks up this ticket should read the trade-offs below and choose; nothing here should be read as final.

For a batch of 150–300 simple, single-page, letterhead-style bills generated once a month and printed locally on A4/Letter, the strongest case is for a **pure-PHP HTML/CSS renderer — dompdf, most likely via `barryvdh/laravel-dompdf` for its direct `Pdf::loadView()` Blade integration, or via `spatie/laravel-pdf`'s DOMPDF driver if the team wants one facade with a documented upgrade path to a Chromium-based driver later.**

**What you get:** no headless-Chrome/Node/Docker/Python runtime to install, patch, or keep alive on whatever server prints these bills; no per-document process-launch overhead (dompdf runs in-process); explicit, documented paper-size and `@page`-margin control (`setPaper('a4'|'letter', ...)`); and a well-defined support boundary (CSS 2.1 + partial CSS3) that a one-page letterhead-and-line-items layout does not exceed, per dompdf's own CSS compatibility table.

**What you give up / risk, explicitly:**

- **PHP 8.5 support is real but layered, and one layer has a documented gap.** `barryvdh/laravel-dompdf`'s own CI does run PHP 8.5 (together with Laravel 13) — so the Laravel-facing glue code is verified on 8.5. But that wrapper's actual rendering work happens inside `dompdf/dompdf`, and **dompdf's own CI matrix stops at PHP 8.4 as of this research date — PHP 8.5 is not yet in dompdf's test suite at all**, even though its composer constraint (`^7.1||^8.0`) permits installing on it. That is a genuine, currently-open gap, not an inference — see §3.3. `mpdf/mpdf` is the only candidate researched here where PHP 8.5 is both declared in `composer.json` _and_ actually run in the project's own CI matrix, and would be the safer choice if verified PHP 8.5 support is the deciding factor, at the cost of losing barryvdh/laravel-dompdf's built-in `Pdf::loadView()` Blade convenience (mpdf needs a manual `view(...)->render()` step) and losing dompdf's wider ecosystem/community size. Practically: this app's own test suite (Pest) generating a real bill PDF on the actual PHP 8.5 runtime is the fastest way to close this gap regardless of which library is chosen — none of these packages' own sources substitute for that check.
- **CSS ceiling.** dompdf/mpdf both explicitly lack flexbox and CSS grid. If the bill's design ever grows past simple block/table layout (e.g., a more visually complex multi-column letterhead), this ceiling could force a rework onto a Chromium-based driver later — spatie/laravel-pdf's multi-driver design exists specifically to make that later switch a one-line `driver()` change rather than a rewrite, which is the main argument for adopting that facade now even while running its DOMPDF driver.
- **No published batch/throughput numbers exist for any candidate.** Every quantitative claim about "150–300 PDFs is fine" here is a qualitative, architectural inference (no subprocess spawn = lower fixed cost per document), not a benchmarked number from any package's own documentation — dompdf's own wiki literally marks its performance-metrics section "_todo_." A proof-of-concept batch run against real bill data and the target server's actual memory/CPU limits is still advisable before committing, since no primary source substitutes for that measurement.
- **Choosing Browsershot/Chrome-PHP/spatie's Chromium drivers instead** would buy full modern CSS (grid/flexbox) and WeasyPrint-grade paged-media control, at the cost of installing and maintaining Node.js + a Chrome/Chromium binary (or Docker, for Gotenberg) on the machine that runs the monthly batch job, plus an architecturally-inherent per-document browser-process cost that pure-PHP rendering doesn't have — a real operational footprint for a task this simple.
- **TCPDF and wkhtmltopdf-based packages are not recommended**: TCPDF's own README calls itself deprecated/maintenance-only and isn't a CSS/Blade-driven renderer to begin with; wkhtmltopdf's own upstream binary repository has been archived (read-only) since January 2023, regardless of how recently its Laravel wrapper was last released.
